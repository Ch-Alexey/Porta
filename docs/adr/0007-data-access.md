# ADR-0007: Доступ к данным — SQLite через Microsoft.Data.Sqlite, миграции вручную

- **Статус:** принято
- **Дата:** 2026-07-30

## Контекст

Ядру нужна локальная БД метаданных: доверенные устройства, хранилища, позже — индекс
файлов/блоков, история версий, индекс медиа. Запросы будут специфичными (сравнение
индексов, выборки блоков), схема — под нашим контролем.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Microsoft.Data.Sqlite + свои миграции** | Лёгкий, полный контроль над SQL и схемой, минимум магии, быстрый старт | Маппинг и миграции пишем сами |
| EF Core (+ SQLite) | Продуктивность, миграции из коробки, LINQ | Тяжелее, «магия», хуже контроль над тонкими запросами синка |
| LiteDB | Простой embedded NoSQL | Нет реляционных запросов, чужой формат, меньше контроля |

## Решение

**Microsoft.Data.Sqlite** (10.0.10) напрямую, с **самодельным раннером миграций**.
Тонкий слой репозиториев поверх ADO.NET. Без EF Core.

Обоснование: движок синхронизации — это в первую очередь аккуратные запросы к индексам
и блокам, где важен контроль над SQL, а не ORM-продуктивность. Это согласуется с общей
линией проекта (лёгкий стек, контроль: ср. выбор MessagePack в [ADR-0004](0004-protocol-format.md)).

## Миграции

- Версия схемы хранится в `PRAGMA user_version`.
- Упорядоченный список миграций (SQL-шаги). Раннер при открытии БД применяет все
  недостающие в транзакции и поднимает `user_version`.
- Миграции только вперёд, аддитивные; номер шага не переиспользуется.

## Настройки соединения

- `PRAGMA journal_mode = WAL` — конкурентное чтение при записи (индексатор + UI).
- `PRAGMA foreign_keys = ON` — целостность связей (хранилище ↔ устройства).
- Одна БД-файл на устройство (путь — в папке данных приложения).

## Последствия

- Зависимость `Microsoft.Data.Sqlite` в `Porta.Core`.
- Репозитории пишем руками; маппинг — простыми ридерами (при росте боли — рассмотреть
  Dapper, но не сейчас).
- Схему и миграции документируем в features/02-data-model.md.
