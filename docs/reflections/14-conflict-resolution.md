# Рефлексия: Этап 4 — разрешение конфликтов (срезы A–C)

Честный самоанализ. Дата: 2026-07-31. Покрывает [14](../features/14-versioned-index.md),
[15](../features/15-conflict-resolution.md), [16](../features/16-conflict-apply.md).

## Что сделал

- **A (версионированный индекс):** `VersionedFileEntry` (файл + version vector),
  `IndexVersioning.Apply` — инкремент счётчика устройства при изменении файла.
- **B (решение):** `ConflictResolver.Decide` (Accept/Skip/Conflict по векторам + сверка
  контента при равных версиях), `ConflictName` (имя конфликтной копии в стиле Syncthing).
- **C (применение):** `SyncApplier.Apply` — принять (с архивом), пропустить или сохранить
  обе версии (конфликтная копия), с отчётом. 15 тестов на трио. Всего 147 юнит-тестов.

## Что получилось хорошо

- **Обе версии при конфликте — реально работают на файлах.** Тест
  `Concurrent_edit_keeps_local_and_writes_conflict_copy` доказывает: параллельная правка
  не теряет ни локальную, ни удалённую версию. Это ровно то поведение, которое
  пользователь выбрал в функциональной картине.
- **Не тронул `FileIndexEntry`.** Версии повесил отдельной обёрткой `VersionedFileEntry` —
  формат контент-индекса и его тесты не пострадали, слои разделены.
- **Переиспользование готового:** `SyncApplier` стоит на `ConflictResolver` +
  `FileAssembler` + `IVersionStore` — конфликтная копия и архив прежней версии получились
  «бесплатно» из уже собранных кубиков.
- **Разбивка на A→B→C** держала каждый срез маленьким и тестируемым; логика конфликта
  проверена изолированно до записи на диск.

## Что бы пересмотрел / техдолг (явно)

1. **Главное: ещё не по сети и не персистентно.** Version vectors живут только в тестовых
   конструкциях. Чтобы конфликты работали между реальными устройствами, нужен срез D:
   обмен `VersionedFileEntry` в протоколе **и** хранение версионированного индекса между
   запусками (иначе при каждом старте вектора «забываются» и всё выглядит новым). Без
   этого фича — доказательство логики, не рабочий двусторонний синк.
2. **Синк всё ещё односторонний.** `SyncApplier` применяет удалённое к локальному; чтобы
   стороны *сошлись*, нужен встречный проход. Сам конфликт-резолвинг к этому готов, но
   оркестрации двустороннего обмена нет.
3. **Конфликтная копия сама попадёт под синхронизацию.** Файл `*.sync-conflict-*` — обычный
   файл в папке; при следующем скане уедет на другие устройства. Возможно, это желаемо
   (Syncthing так и делает), но стоит осознанно решить и, может, дать игнор по умолчанию.
4. **Имя конфликта — только по `remoteDeviceId`.** Точнее было бы брать устройство из
   «выигравшей» ветки вектора; сейчас передаём peer'а. Для двух устройств совпадает, для
   многих — уточнить.
5. **Version vector не растёт при приёме.** Когда принимаем удалённую версию (Accept),
   надо бы сохранить/смёржить её вектор в свой индекс. `SyncApplier` пишет файл, но не
   возвращает обновлённый версионированный индекс — это часть среза D (персистентность).

## Вывод по процессу

Ядро разрешения конфликтов собрано и проверено на файлах: логика векторов → решение →
запись обеих версий. Разбивка на три маленьких среза себя оправдала. Но честно повторю
долг №1: **без обмена версиями по сети и их персистентности это пока логика, а не рабочий
двусторонний синк** — и именно срез D (протокол + хранение версий) превращает всё
собранное в настоящую двустороннюю синхронизацию с конфликтами.
