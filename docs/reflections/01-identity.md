# Рефлексия: Этап 1 — Identity (первый срез)

Честный самоанализ по завершённому куску. Дата: 2026-07-30.

## Что сделал

`Base32` (RFC 4648), `DeviceId` (Base32 от SHA-256 публичного ключа), `DeviceIdentity`
(ECDSA P-256 + подпись/проверка), `IDeviceIdentityStore` + `FileDeviceIdentityStore`.
28 модульных тестов, все зелёные. Контекст — в docs/features/01-identity.md.

## Что получилось хорошо

- **Чистое разделение слоёв.** Крипто и идентити не тянут за собой ни UI, ни платформу.
  Ядро осталось платформонезависимым, как задумано в архитектуре.
- **Абстракция хранилища ключа** (`IDeviceIdentityStore`) введена сразу — замена
  файлового хранения на защищённое не заденет остальной код.
- **Тесты на реальных векторах** RFC 4648, а не «на глаз». Проверены детерминизм ID,
  round-trip персистентности, кросс-проверка подписи чужим ключом.
- **Обоснованный выбор ECDSA P-256** (а не Ed25519) — не по привычке, а под будущий
  QUIC/TLS. Зафиксирован в ADR, чтобы потом не спорить с самими собой.

## Что бы пересмотрел / техдолг (явно)

1. **Приватный ключ лежит на диске в открытом виде.** Права 0600 на POSIX — слабая
   защита; на Windows ACL вообще не ограничили. Это **реальный долг по безопасности**,
   закрыть до любого релиза (DPAPI/Keychain/Keystore). Уже в roadmap.
2. **Нет контрольных цифр в Device ID.** При ручном вводе опечатку не поймаем.
   Syncthing использует Luhn mod N. Отложено осознанно, но пометить как UX-риск для
   pairing.
3. **Гонка в `LoadOrCreate`.** Если два потока/процесса вызовут одновременно при
   отсутствии файла — создадут две личности, одна перезапишет другую. Для старта
   приложения риск низкий (одиночный вызов), но стоит сделать идемпотентно/под замком,
   когда появится DI и жизненный цикл личности.
4. **Схема подписи без доменного разделения.** Сейчас `Sign(data)` — «сырая» подпись
   над произвольными байтами. Для протокола связывания (Этап 2) нужно добавить
   контекст/префикс, чтобы подпись из одного сценария нельзя было переиспользовать в
   другом. Заложить при проектировании pairing.
5. **`Base32.Decode` аллоцирует `List<byte>`.** Для коротких ID неважно, но если код
   переиспользуют для больших данных — переписать на буфер. Пока не трогаю (YAGNI).

## Риски, за которыми следить

- Совместимость ECDSA-ключа с TLS-сертификатом для QUIC — проверить на этапе транспорта
  фактической генерацией сертификата, а не только в теории.
- Формат PKCS#8 при миграции на защищённое хранилище — убедиться, что импорт/экспорт
  переживёт смену бэкенда.

## Вывод по процессу

Документация-до-кода сработала: объём был понятен заранее, scope не расползся.
Дисциплина «фича = md-контекст + тесты» держит качество. Дальше — не забывать
доменное разделение подписи и не копить долг по хранению ключа.
