# Рефлексия: Этап 2 — Pairing (логика связывания)

Честный самоанализ. Дата: 2026-07-30.

## Что сделал

Формат токена связывания (`PairingToken`) с публичным ключом инициатора внутри, кодек
для QR/ссылки (MessagePack → Base64Url → `porta:`), доменно-разделённое сообщение-
доказательство (`PairingMessage`), сервис связывания (`PairingService`: приглашение,
доказательство joiner'а, проверка на инициаторе, установление доверия) с управляемым
`TimeProvider`. 62 теста в ядре, зелёные.

## Что получилось хорошо

- **Якорь доверия в QR, а не в сети.** Токен несёт сам публичный ключ инициатора —
  joiner закрепляет его из аутентичного канала (QR), сеть лишь доказывает владение.
  Это сильнее, чем передавать ключ по сети и надеяться.
- **Закрыт долг из рефлексии Identity:** подпись доменно-разделённая (контекст
  `porta.pairing.v1` + length-prefixed поля). Подпись из связывания нельзя переиграть
  в другом сценарии. Тест на «подпись чужим ключом» это стережёт.
- **Типизированные исходы вместо исключений** (`PairingResult`): ожидаемые провалы
  (просрочка, несовпадение личности, плохая подпись) — это данные, а не аварии.
- **Управляемое время** через `TimeProvider` — просрочка тестируется честно, без
  Thread.Sleep.
- **Недоверенные данные помечены:** декодер токена использует `MessagePackSecurity.
  UntrustedData` — вход-то из чужого QR.

## Что бы пересмотрел / техдолг (явно)

1. **Нет rate-limit / защиты от перебора кода.** Секрет 32 байта — перебор нереален,
   но сам протокол проверки не ограничивает попытки. Когда появится сетевой обмен,
   добавить лимит попыток и одноразовость (секрет сгорает после успеха/N попыток).
2. **Одноразовость секрета не enforced в логике.** `VerifyProof` можно вызвать дважды
   с тем же токеном. Нужно, чтобы инициатор инвалидировал приглашение после успеха —
   это состояние (список pending-приглашений), которого в этом срезе нет намеренно.
3. **`record` + `byte[]` = сравнение по ссылке.** Наступил на это в тесте round-trip.
   Не баг рантайма, но `PairingToken`/`TrustedDevice` с byte[] коварны в равенстве —
   если где-то понадобится структурное сравнение, придётся писать `Equals` вручную или
   обернуть ключи в тип со значимым равенством. Пометить на случай использования в
   коллекциях/сравнениях.
4. **Взаимность доверия асимметрична по слоям.** joiner доверяет из токена (офлайн),
   инициатор — из подписи (тоже офлайн), но фактическая проверка «сеть предъявила тот
   самый ключ» отложена в транспорт. Риск: если забыть эту проверку на Этапе 3, доверие
   повиснет. Явно записать как обязательный шаг сетевого хендшейка.
5. **Адреса в токене — сырые строки.** Ни валидации формата, ни ограничения на приватные
   диапазоны. При выходе за LAN (позже) это станет вектором (SSRF-подобное «подключись
   куда скажу»). Валидацию адресов заложить на этапе транспорта/discovery.

## Вывод по процессу

Разбор протокола в md перед кодом снова окупился: доменное разделение и «ключ в QR»
были продуманы до написания, а не по факту. Главные долги — состояние приглашений
(одноразовость + rate-limit) и обязательная сетевая проверка ключа; оба естественно
всплывут на Этапе 3, когда pairing поедет по QUIC. Пока логика полная и изолированная.
