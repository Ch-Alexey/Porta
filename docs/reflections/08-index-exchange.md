# Рефлексия: Этап 3 — обмен индексами и дельта

Честный самоанализ. Дата: 2026-07-31.

## Что сделал

Разметил доменные типы индекса (`FileIndexEntry`, `ChunkInfo`) для MessagePack,
`FolderIndexMessage` (индекс на проводе), `IndexComparer` → `IndexDiff` (какие файлы
новые/изменившиеся, какие блоки догрузить, с дедупликацией). 6 юнит-тестов +
интеграционный обмен поверх QUIC. Всего 90 юнит + 6 интеграционных.

## Что получилось хорошо

- **Дельта считается по-настоящему, с дедупликацией.** Тесты фиксируют ключевую
  ценность: изменившийся файл требует только изменившийся блок; блок, уже лежащий в
  другом локальном файле, не запрашивается. Это и есть экономия rsync-типа.
- **Удаления не распространяются** — заложено в самой логике (итерируем только
  удалённые записи), и тест `Local_only_file_is_ignored` это стережёт. Совпадает с
  продуктовым решением.
- **Формат протокола прямо на доменных типах** (ADR-0004): round-trip реального вывода
  `FolderScanner` через канал прошёл — значит и `DateTimeOffset`, и `byte[]`, и
  вложенные блоки летают без отдельных DTO.
- **Сквозная проверка поверх QUIC** — не просто «сравнили два списка в памяти», а
  «сериализовали, передали по шифрованному каналу, разобрали, посчитали дельту».

## Что бы пересмотрел / техдолг (явно)

1. **Индекс целиком в одном сообщении.** `FolderIndexMessage` несёт весь список файлов
   и блоков разом. На большом хранилище это упрётся в `MaxMessageSize` (16 МБ) и в
   память. Нужен потоковый/постраничный обмен индексом (по файлу/пачками) — обязательно
   до реальных объёмов.
2. **Сравнение по контент-хешу целиком.** Если поменялся 1 байт — контент-хеш другой,
   файл целиком в `FilesToUpdate` (это ок), но мы не переиспользуем его старые блоки как
   «локально присутствующие», если старой версии нет в индексе. На деле старые блоки
   есть на диске — стоит учитывать блоки текущей локальной версии файла (мы учитываем
   все локальные блоки, так что частично покрыто; проверить край с переименованием).
3. **Нет направления/ролей синка.** Пока «сторона B посчитала, чего ей не хватает от A».
   Двусторонний синк (оба обмениваются и сходятся), режимы (только приём/отдача),
   version vectors для конфликтов — впереди (Этап 4).
4. **`NeededBlock` без привязки к файлу/смещению.** Для сборки файла нужно знать, куда
   какой блок класть. Сейчас дельта даёт список файлов и список блоков раздельно;
   при передаче/сборке понадобится карта «файл → последовательность блоков» (она есть в
   `FileIndexEntry.Chunks`, просто пока не связана в план сборки).
5. **Нет проверки полноты/повреждений на приёме.** Когда блоки поедут, надо сверять их
   хеши и итоговый контент-хеш файла. Заложить при передаче блоков.

## Вывод по процессу

Слой лёг на всё готовое: индекс сериализуется на доменных типах, дельта — чистая функция
с понятными тестами, а сквозная проверка поверх QUIC подтвердила, что цепочка
«скан → сериализация → канал → разбор → дельта» рабочая. Главные долги —
масштабирование обмена индексом (не «всё одним сообщением») и план сборки файла из
блоков; оба всплывут в следующем срезе (передача блоков и сборка файла), который и даст
первую реальную синхронизацию файла.
