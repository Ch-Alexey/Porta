# Рефлексия: Этап 3 — передача блоков и сборка файла

Честный самоанализ. Дата: 2026-07-31.

## Что сделал

Сообщения запроса/ответа блоков, `FolderBlockReader` (отдача блоков из файлов по хешу),
источники блоков (`IBlockSource` + память/папка/композит), `FileAssembler` (сборка файла
с проверкой хешей, атомарной записью, сохранением mtime, защитой от path traversal).
7 юнит-тестов + интеграционный **полный синк файла поверх QUIC**. Всего 97 юнит + 7
интеграционных.

## Что получилось хорошо

- **Первая реальная синхронизация файла работает end-to-end** и доказана тестом:
  скан → индекс → дельта → запрос блоков → передача по шифрованному QUIC → сборка →
  побайтовое совпадение. Это соединило всё, что делали с Этапа 1.
- **Безопасность заложена сразу, не «потом»:** проверка хеша каждого блока и итогового
  контент-хеша (защита от повреждения/подмены) + защита от path traversal (закрыт кусок
  долга из рефлексии индексатора — вредоносный `../` путь отвергается, тест это стережёт).
- **Атомарная запись** (temp-файл + move) — при сбое на середине не остаётся битого
  файла; на исключении temp удаляется.
- **Дедупликация переиспользована в сборке:** `CompositeBlockSource` берёт блок сперва
  из полученных, потом из локальных файлов — то есть уже имеющиеся на диске блоки не
  качаются повторно (согласовано с дельтой из `IndexComparer`).

## Что бы пересмотрел / техдолг (явно)

1. **Всё в память.** Блоки запрашиваются и передаются одним `BlockResponseMessage`,
   собираются в `MemoryBlockSource`. Для большого файла/множества файлов это упрётся в
   память и `MaxMessageSize`. Нужна потоковая передача блоков (по одному/пачками) и
   сборка на лету — до реальных объёмов обязательно.
2. **Нет версионирования.** `FileAssembler` перезаписывает файл. Продукт требует историю
   версий и «не терять данные». Перед перезаписью существующего файла надо сохранять
   предыдущую версию (Этап 4). Сейчас перезапись — молчаливая.
3. **Нет разрешения конфликтов.** Если у принимающего файл тоже менялся — мы его просто
   перезапишем. Version vectors и «обе версии при конфликте» — впереди.
4. **Оркестрация «руками» в тесте.** Последовательность index→request→response написана
   в тесте, а не в переиспользуемом сервисе синхронизации. Нужен `SyncSession`/движок,
   который ведёт этот диалог для целого хранилища (много файлов, порядок, прогресс,
   ошибки). Пока это только доказательство работоспособности.
5. **Один запрос — один ответ, без параллелизма и backpressure.** Реальному синку нужны
   конвейер запросов и ограничение памяти/скорости.
6. **`ResolveSafePath` — только про `..`.** Симлинки внутри папки (выводящие наружу) не
   проверяются; на POSIX симлинк может увести за пределы. Долг из индексатора про симлинки
   ещё не закрыт полностью.

## Вывод по процессу

Это кульминация трёх этапов: впервые «файл реально уехал с одного узла на другой» —
безопасно, дельтой, с проверками. Дисциплина «чистое ядро + тесты, интеграция поверх
реального QUIC» довела до работающего синка одного файла. Но честно: это **доказательство
цепочки, а не готовый движок** — главные долги (потоковость, версии, конфликты,
оркестрация целого хранилища) — это уже Этап 4, и без них синк не «боевой».

## Итог Этапа 3

Транспорт (QUIC + pinning), сессия (доверие + рукопожатие), обмен индексами, дельта и
передача блоков со сборкой — всё есть и связано. Один файл синхронизируется between two
devices по-настоящему. Дальше — Этап 4: движок синхронизации целого хранилища,
версионирование и конфликты (version vectors).
