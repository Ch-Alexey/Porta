# Рефлексия: Этап 4 — движок синхронизации (оркестрация)

Честный самоанализ. Дата: 2026-07-31.

## Что сделал

`SyncProtocol` (`ServeAsync`/`PullAsync`) — переиспользуемый диалог pull целого
хранилища поверх `MessageChannel`; `FolderIndexRequest`, `SyncResult`. Тестовый помощник
`ConnectedChannels` (пара связанных in-memory каналов через `System.IO.Pipelines`).
3 функциональных теста без сети + интеграционный поверх QUIC. Всего 100 юнит + 8
интеграционных.

## Что получилось хорошо

- **Логика синка отвязана от транспорта.** Движок работает поверх `MessageChannel`, и
  это дало возможность тестировать полный диалог **в памяти, без libmsquic** — быстро и
  детерминированно. Один тест поверх QUIC подтверждает, что связка с реальным транспортом
  тоже работает. Раньше это был бы «ручной» код в интеграционном тесте.
- **`ConnectedChannels` — правильный инструмент, который я раньше откладывал.** В
  рефлексии по протоколу я избегал дуплекс-стрима; здесь он окупился и снял зависимость
  тестов синк-логики от QUIC. Стоило сделать раньше.
- **Синк целого хранилища, а не одного файла:** вложенные папки, пропуск совпадающих
  файлов, пустой источник — покрыто тестами.
- **`SyncResult`** даёт наблюдаемость (сколько файлов/блоков/байт) — пригодится для UI и
  прогресса.

## Что бы пересмотрел / техдолг (явно)

1. **Только односторонний pull за один проход.** Реальный синк двусторонний: оба узла
   должны обменяться и сойтись. Сейчас «B тянет у A». Нужен встречный проход или
   объединённый протокол. Плюс — режимы хранилища (только приём/отдача) пока не учитываются.
2. **Всё ещё не потоково.** Индекс и блоки — по одному большому сообщению. На больших
   хранилищах упрётся в память и `MaxMessageSize`. Это главный технический долг перед
   реальными объёмами; тянется с [08]/[09].
3. **Нет версионирования и конфликтов.** `PullAsync` перезаписывает файлы через
   `FileAssembler` без сохранения предыдущей версии и без проверки, менялся ли файл у
   принимающего. Продуктовое требование «не терять данные» пока не выполнено — это
   следующий приоритет Этапа 4.
4. **Нет прогресса/отмены на середине.** `CancellationToken` пробрасывается, но частичный
   результат/возобновление не поддержаны. При обрыве — начинаем заново.
5. **Сервер не проверяет `storageId`.** `ServeAsync` игнорирует, какое хранилище
   запрошено, и отдаёт указанную папку. Когда хранилищ несколько, нужно сопоставление
   `storageId → папка` (из репозитория) и отказ для неизвестного/недоступного.
6. **Ошибки диалога.** Если одна сторона упадёт/пришлёт не то сообщение — поведение не
   определено (исключение десериализации). Нужны явные ошибки протокола и корректное
   закрытие.

## Вывод по процессу

Хороший рефакторинг-срез: «доказательство цепочки» из Этапа 3 стало переиспользуемым
движком, а тесты синка перестали зависеть от QUIC. Но честно: это всё ещё **односторонний
pull без версий и конфликтов** — то есть «скопировать новое/изменённое с A на B», а не
полноценная двусторонняя синхронизация с сохранением истории. Следующий и, пожалуй,
самый важный для продукта долг — **версионирование при перезаписи** (не терять данные),
затем двусторонний синк и потоковость.
