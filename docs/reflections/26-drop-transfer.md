# Рефлексия: 26. Разовая передача — протокол (срез 1, ядро)

## Что сделал

Протокол (`src/Porta.Core/Protocol/`):
- `SessionIntentMessage` — инициатор объявляет намерение сессии (Sync/Drop) сразу после
  рукопожатия. Раньше сессия молча означала синк.
- `DropMessages` — предложение, решение, заголовок файла, куски содержимого, подтверждение.
- `ProtocolVersion` 1 → 2 (диалог изменился; релиза не было, мигрировать нечего).

Ядро (`src/Porta.Core/Drop/`):
- `DropProtocol` — потоковая отправка и приём: предложение → подтверждение → содержимое
  кусками по 256 КиБ → подтверждение приёма.
- `IDropAcceptance` / `DropDecision` — вопрос «принимать?» задаёт ядро, отвечает UI;
  решение несёт и папку назначения, поэтому ядро не знает про настройки.
- `SafePath` — вынес из приватного метода `FileAssembler`, теперь общий.

`SyncService` научился отправлять (`SendFilesAsync`) и маршрутизировать входящее
соединение по намерению.

Тесты: 9 в `Porta.Core.Tests/Drop` + 2 интеграционных поверх настоящего QUIC.
Итого 239 зелёных, Release 0 предупреждений.

## Что получилось хорошо

**Нашёл и подтвердил серьёзный дефект в уже работающем синке.** Когда решал, брать ли
для передачи готовый блочный обмен, заметил, что `BlockResponseMessage` складывает все
блоки в одно сообщение при лимите канала в 16 МБ. Не поверил себе на слово — собрал
одноразовую пробу и прогнал синк папки с файлом 20 МБ:

```
отдающая сторона: InvalidOperationException «Сообщение больше лимита 16777216 байт»
принимающая сторона: WaitingForActivation — висит вечно
```

Оказалось хуже, чем я предполагал: я ждал падения отправителя, а получатель ещё и
зависает навсегда — таймаута на чтение нет. Синхронизация папки с фотографиями
упирается в это сразу. Записал в `docs/features/26-drop-transfer.md` как кандидата в
блокеры релиза. Пробу удалил, чтобы не тащить в репозиторий тест, фиксирующий баг.

**Смена протокола сломала сборку в нужных местах.** Добавил `intent` пятым параметром
`EstablishAsync` — компилятор показал все 12 позиционных вызовов в интеграционных
тестах. Это лучше, чем добавить параметр в конец и получить тихо разошедшиеся стороны.

**Отказ — это тоже нормальный исход, а не ошибка.** Если приём не настроен, ядро
отвечает вежливым `DropDecision.Reject`, а не рвёт соединение: отправитель видит
причину. Отдельный интеграционный тест на этот путь.

**Безопасность проверял злыми тестами, а не намерениями.** Путь `../../evil.txt` в
предложении, подменённый контент-хеш, совпадение имени с существующим файлом — на всё
есть тест, который проверяет ещё и что на диске ничего не осталось.

## Решения, которые стоит оспорить

**Передача не переиспользует content-defined chunking.** Осознанно: у разового
получателя нет прежней версии, дельту считать не с чем, CDC дал бы только расход CPU.
Плата — второй путь записи файла на диск рядом с `FileAssembler`. Общее у них теперь
только `SafePath`. Если появится возобновление прерванной передачи, эти пути,
возможно, придётся сводить.

**`SyncService` перестал быть только про синк.** Он держит транспорт, личность и
доверие, поэтому передачу естественно повесить туда же — но имя теперь врёт, класс по
факту `PeerService`. Не стал переименовывать ради пяти файлов; долг записан здесь.

## Техдолг и оговорки

- **UI нет.** Это ядро. Отправить или принять из приложения пока нельзя — `BackgroundSyncListener`
  вызывает `ServeOnceAsync` без `IDropAcceptance`, то есть входящие передачи сейчас
  вежливо отклоняются. Это срез 27, и без него фича пользователю не видна.
- **Прогресса нет.** Результат приходит по завершении; на файле в несколько гигабайт
  пользователь будет смотреть в неподвижный экран. Каркас (куски по 256 КиБ) для
  прогресса готов, событие не выведено.
- **Возобновления нет.** Обрыв на 90% — передавать заново.
- **Отмену получателем в процессе не предусмотрел.** Согласие спрашивается один раз, до
  содержимого; передумать по ходу нельзя.
- **`.porta-drop`-времянки при жёстком обрыве остаются** в папке назначения. Удаляются
  при обычной ошибке (`catch`), но не при падении процесса.
- **Все файлы предложения принимаются или отклоняются целиком** — выбрать «эти беру,
  эти нет» нельзя.

## Долг, который всё ещё тянется

Переинициализация `FileSystemChangeNotifier` при изменении списка хранилищ — не тронул
третий срез подряд. Записываю честно, а не тихо.
