# Рефлексия: Этап 4 — версионирование

Честный самоанализ. Дата: 2026-07-31.

## Что сделал

`IVersionStore` + `FileSystemVersionStore` (архив копии с меткой времени вне папки
хранилища, `ListVersions`, `TimeProvider`), интеграция в `FileAssembler.Write` (архив
перед заменой существующего файла) и `SyncProtocol.PullAsync`. 7 тестов. Всего 106 юнит
+ 8 интеграционных.

## Что получилось хорошо

- **Продуктовое обещание «не терять данные» выполнено на уровне синка.** Тест
  `Overwriting_changed_file_preserves_previous_version` доказывает: старое содержимое
  уходит в версии до перезаписи. Это то, что пользователь подчёркивал с самого начала.
- **Безопасный порядок операций:** архивируем существующий файл **до** атомарного
  перемещения нового; при сбое архива новый файл ещё не на месте, старый цел.
- **Абстракция `IVersionStore`** — политику хранения/бэкенд можно менять, не трогая
  сборку. Опциональный параметр: без него поведение прежнее (не ломает существующее).
- **Управляемое время** (`TimeProvider`) — порядок версий по времени проверяется честно.

## Что бы пересмотрел / техдолг (явно)

1. **Ловушка «версии внутри синкаемой папки».** Пришлось хранить версии вне папки
   хранилища, иначе сканер их подхватит и начнёт синхронизировать. Это костыль до
   появления **игнор-паттернов** — с ними можно держать `.porta/versions` внутри и
   исключать из скана. Пока обязанность «versionsRoot вне папки» на вызывающем — легко
   ошибиться.
2. **Нет политики хранения.** Версии копятся бесконечно — раздуют диск. Нужны лимиты
   (число версий / срок / общий размер) и очистка. Обязательно до реального использования.
3. **Копирование, а не перемещение.** `File.Copy` архивирует, потом файл перезаписывается —
   лишнее чтение/запись. Для больших файлов дороговато; можно было бы move старого в
   версии, а новый писать на его место. Но move усложняет атомарность — оставил copy,
   пометил.
4. **Коллизия по времени.** Метка времени с миллисекундами; два архива в одну
   миллисекунду → `File.Copy(overwrite:false)` бросит. Маловероятно, но нужен суффикс-счётчик.
5. **Восстановление — только «файлы лежат».** `ListVersions` отдаёт пути, но
   восстановление (положить версию обратно, желательно тоже через архив текущей) как
   операции нет. Для UI понадобится `Restore`.
6. **Версии при удалении не покрыты.** Удаления мы не распространяем, но когда появится
   «подсветка отсутствующих» и, возможно, удаление по желанию — удаляемый файл тоже стоит
   архивировать.

## Вывод по процессу

Небольшой, но важный для продукта срез: закрыл ключевое обещание «история/не терять
данные» там, где раньше была молчаливая перезапись. Главный связанный долг — **игнор-
паттерны** (чтобы служебные папки вроде версий не синхронизировались) и **политика
хранения версий**; оба всплыли прямо здесь. Следующий крупный концептуальный шаг —
version vectors и разрешение конфликтов (сейчас синк односторонний и «победитель —
источник»).
