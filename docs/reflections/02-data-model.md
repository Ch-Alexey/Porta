# Рефлексия: Этап 1 — модель данных + SQLite (первый срез)

Честный самоанализ. Дата: 2026-07-30.

## Что сделал

`PortaDatabase` (соединения с WAL + foreign_keys, раннер миграций на `user_version`),
миграция 001 (таблицы `devices`, `storages`, `storage_devices`, `settings`), модели
`TrustedDevice`/`Storage`/`StorageDeviceLink`, репозитории устройств и хранилищ (CRUD,
привязка устройств, upsert, каскадное удаление, проверка FK). Итого в ядре 39 тестов,
все зелёные.

## Что получилось хорошо

- **Свой раннер миграций** вышел маленьким и понятным: версия в `user_version`, шаги
  в транзакции. Без EF-магии, ровно как решили в ADR-0007.
- **Тесты бьют по важному:** round-trip BLOB публичного ключа, сохранение enum'ов,
  upsert-семантика привязки, каскады и реальное срабатывание внешнего ключа
  (`foreign_keys=ON` проверяется, а не предполагается).
- **Параметризованный SQL** везде — никаких конкатенаций пользовательских данных.
- **Модели-record** дали бесплатное сравнение по значению — тест `Assert.Equal(storage, loaded)`
  проверяет все поля разом.

## Что бы пересмотрел / техдолг (явно)

1. **Соединение на каждый вызов репозитория.** Просто и безопасно, но для будущего
   индексатора (много операций подряд) — накладно, и нет способа выполнить несколько
   операций в одной транзакции (напр. «создать хранилище + привязать устройства»
   атомарно). Ввести Unit-of-Work / передавать транзакцию, когда появится синк.
2. **`PortaDatabase.Migrate()` без внешней синхронизации.** Если два процесса откроют
   БД впервые одновременно — гонка миграций. WAL спасает от части проблем, но явную
   блокировку/`BEGIN IMMEDIATE` стоит добавить, когда появятся фоновые процессы.
3. **Нет валидации на уровне моделей.** `Storage.LocalPath` может быть пустым/битым,
   `Name` — пустым. Сейчас доверяем вызывающему. Валидацию добавить на границе
   (сервисный слой создания хранилища), не в записи.
4. **`storage_id` — просто строка.** Нет типа-обёртки и генерации ID (в отличие от
   `DeviceId`). Пока ID задаёт вызывающий, что рискованно. Нужен `StorageId` с
   генерацией (напр. случайные байты → Base32) — сделать вместе с фичей создания
   хранилища.
5. **Индексов под будущие запросы нет.** Пока таблицы маленькие — неважно, но при
   индексе файлов/блоков забыть про индексы будет больно. Помнить при миграциях 002+.

## Внешние сюрпризы

- **Уязвимость в нативном SQLite** (`SQLitePCLRaw.lib.e_sqlite3` 2.1.11, High) прилетела
  транзитивно через `Microsoft.Data.Sqlite`. Закрыл пином `2.1.12` + включил
  `CentralPackageTransitivePinningEnabled`. Урок: проверять NU1903 не только на прямых
  зависимостях — транзитивные тоже. Второй раз за проект утыкаемся в уязвимость пакета
  (до этого — MessagePack); стоит завести привычку гонять `dotnet list package
  --vulnerable` перед вехами.

## Вывод по процессу

Схема-в-md перед кодом снова окупилась: таблицы и связи были обдуманы заранее, писать
репозитории было механически. Главный архитектурный долг на ближайшее — транзакции/
Unit-of-Work и типизированный `StorageId`; и то, и другое естественно закрыть на этапе
«создание хранилища».
