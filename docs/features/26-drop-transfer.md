# 26. Разовая передача: протокол (срез 1, ядро)

## Зачем

`00-functionality.md` §4.2 обещает вторую половину продукта: не только настроенные
хранилища, но и «просто передать файлы на другое устройство» — без постоянной связи,
без отслеживания изменений. Это же действие нужно вкладке «Медиа»: найти фото и
**отправить** (§4.5). Сейчас передать что-либо можно только через хранилище.

Ключевое требование пользователя: **получатель подтверждает приём**. Никто не может
залить файлы на чужое устройство молча, даже будучи доверенным.

## Границы среза

**Входит (ядро):**
- Намерение сессии (`SessionIntent`): после рукопожатия инициатор говорит, чего хочет —
  синхронизацию или разовую передачу. Раньше сессия всегда означала синк.
- Сообщения разовой передачи и потоковая отправка содержимого.
- Подтверждение приёма через абстракцию `IDropAcceptance` (ядро не знает про UI).
- Приём в папку назначения с сохранением метаданных и **без затирания** существующих
  файлов.
- Маршрутизация на принимающей стороне: одно соединение → синк или передача.

**Не входит (следующий срез):**
- UI: вкладка «Отправить», выбор файлов, диалог «Принять файлы от устройства A?»,
  настройка папки «Загрузки». Это срез 27.
- Прогресс передачи в процентах (сейчас — результат по завершении).
- Возобновление прерванной передачи.

## Почему передача НЕ переиспользует блочный обмен синка

Синк умеет отдавать только изменившиеся блоки — это его смысл. У разовой передачи
дельты нет: у получателя файла ещё не было, сравнивать не с чем. Content-defined
chunking здесь дал бы только расход CPU.

Есть и жёсткая техническая причина. `MessageChannel.MaxMessageSize` = 16 МБ, а
`BlockResponseMessage` складывает **все** запрошенные блоки в одно сообщение. Значит
через блочный обмен нельзя передать больше ~16 МБ новых данных за раз, а разовая
передача — это ровно видео и пачки фото.

**Это существующий дефект синка, а не только передачи** (см. «Найденное» ниже).
Чинить его здесь не буду — это отдельный срез по работающему коду; передача же с
самого начала пишется потоковой.

## Протокол

После `HelloMessage` инициатор шлёт намерение — это ломает совместимость со старым
диалогом (раньше сразу шёл `FolderIndexRequest`), поэтому **`ProtocolVersion` → 2**.
Релиза не было, мигрировать нечего.

```
инициатор                        получатель
---------                        ----------
SessionIntent(Drop)          ->
DropOffer(id, files[], total)->
                             <-  DropDecision(accepted, reason?)
   (если отклонено — диалог окончен)
для каждого файла:
  DropFileHeader(path, size, modifiedAt, contentHash) ->
  DropChunk(data, isLast=false) ->   (много раз)
  DropChunk(data, isLast=true)  ->
                             <-  DropComplete(filesReceived)
```

- Содержимое режется буфером 256 КиБ — память не зависит от размера файла, и сообщение
  всегда далеко от лимита в 16 МБ.
- `DropChunk.IsLast` завершает файл явно (пустой последний блок — корректный случай
  для пустого файла).
- `ContentHash` из заголовка проверяется получателем по мере записи: подменённое или
  побитое содержимое не попадёт в папку.

## Приём

`IDropAcceptance.DecideAsync(offer, senderDeviceId, ct)` → `DropDecision`. Реализация
живёт в UI (срез 27) и показывает пользователю диалог; ядро только спрашивает.
Решение несёт и **папку назначения** — так ядро не знает про настройки.

Гарантии на записи:
- путь из предложения санируется (`SafePath.Resolve`, общий с `FileAssembler`) —
  `../` не выведет за пределы папки назначения;
- запись во временный файл, проверка контент-хеша, потом перемещение;
- **существующие файлы не затираются**: при совпадении имени добавляется ` (2)`, ` (3)`.
  Это в духе решения «не удалять совсем» — разовая передача не должна уничтожать данные;
- `mtime` восстанавливается из заголовка (метаданные при передаче не стираются, §4.2).

Если получатель отказал — отправитель узнаёт причину и ничего не шлёт.

## Маршрутизация

`SyncService.ServeOnceAsync` теперь читает намерение и вызывает либо версионированный
синк, либо приём передачи. Если `IDropAcceptance` не передан, передача вежливо
отклоняется («приём не настроен»).

## Найденное по ходу (не чиню в этом срезе)

**Потолок 16 МБ в блочном обмене синка — подтверждён экспериментом.** `VersionedSync` и
`SyncProtocol` кладут все запрошенные блоки в одно `BlockResponseMessage`. Прогнал
синк папки с файлом 20 МБ через in-memory дуплекс:

```
отдающая сторона: InvalidOperationException «Сообщение больше лимита 16777216 байт»
принимающая сторона: WaitingForActivation — висит вечно
```

То есть при передаче больше ~16 МБ новых данных за один синк отдающая сторона падает,
а **принимающая зависает навсегда** — таймаута на чтение нет. Плюс `MemoryBlockSource`
держит все полученные блоки в памяти.

Синхронизация папки с фотографиями упирается в это сразу, так что это **кандидат в
блокеры релиза**, а не косметика. Лечится пакетной отдачей блоков (и таймаутом на
чтение) — отдельный срез по работающему коду, сюда не мешаю.

## Тесты

- Полный успешный обмен по in-memory дуплексу: файлы приходят с содержимым, mtime,
  структурой подпапок.
- Отказ получателя: отправитель не шлёт содержимое, результат помечен отказом.
- Файл больше лимита сообщения (>16 МБ) проходит — доказывает потоковость.
- Битый контент-хеш → файл не появляется в папке назначения.
- Путь с `../` в предложении → отклоняется, наружу ничего не пишется.
- Совпадение имени → рядом появляется ` (2)`, оригинал цел.
- Пустой файл передаётся.
- Маршрутизация: сессия с намерением Sync ведёт себя как раньше.
- Интеграционный тест поверх настоящего QUIC.
