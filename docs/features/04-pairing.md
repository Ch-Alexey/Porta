# Фича: Pairing — связывание устройств

**Статус:** первый срез готов (62 теста в ядре, зелёные) · **Слой:** `Porta.Core/Pairing`

Реализовано: `PairingToken` + `PairingTokenCodec` (MessagePack → Base64Url → `porta:`),
`PairingMessage` (доменно-разделённая подпись), `PairingResponse`, `PairingResult`,
`PairingService` (invite/proof/verify/inviter-trust) с управляемым временем.

## Зачем

Два устройства должны один раз установить **взаимное доверие**: обменяться публичными
ключами так, чтобы этому обмену можно было верить. Канал доверия — **QR-код / ссылка**,
которые пользователь физически переносит с устройства A на устройство B (аутентичный
канал вне сети). См. общую картину в [features/00-functionality](00-functionality.md)
и модель доверия в [ADR-0006](../adr/0006-transport-quic.md).

Терминология: **инициатор (inviter)** — устройство A, показывающее QR; **присоединяющийся
(joiner)** — устройство B, сканирующее QR.

## Ключевая идея

Токен в QR несёт **сам публичный ключ инициатора**, а не только его хеш. Значит joiner
закрепляет (pins) ключ A прямо из QR — якорь доверия в аутентичном канале (QR), а не в
сети. Сеть потом лишь обязана доказать, что она владеет этим ключом (TLS-хендшейк с
совпадающим сертификатом — Этап 3).

В обратную сторону: инициатор изначально не знает joiner'а, поэтому joiner **доказывает**
владение одноразовым кодом из QR и связывает доказательство со своей личностью подписью.

## Токен связывания (`PairingToken`)

Поля (сериализация — MessagePack, [ADR-0004](../adr/0004-protocol-format.md)):

| Поле | Тип | Назначение |
|---|---|---|
| `Version` | int | Версия формата токена (сейчас 1) |
| `InviterPublicKey` | byte[] | Публичный ключ A (SPKI, DER) — joiner его закрепляет |
| `Addresses` | string[] | Сетевые адреса A для подключения |
| `Secret` | byte[] | Одноразовый код (случайные байты), доказывает подлинность joiner'а |
| `ExpiresAtUnix` | long | Срок годности токена (Unix, сек) |

`InviterDeviceId` не хранится — вычисляется из `InviterPublicKey` (это и есть его хеш).

**Кодирование для QR/ссылки** (`PairingTokenCodec`): MessagePack → Base64Url →
строка с префиксом `porta:`. QR-картинку рисует UI из этой строки; ядро остаётся чистым.
Декодирование помечает данные как недоверенные (`MessagePackSecurity.UntrustedData`).

## Доказательство joiner'а (доменно-разделённая подпись)

Чтобы подпись из связывания нельзя было переиспользовать в другом контексте, подписываем
**доменно-разделённое** сообщение (закрывает техдолг среза Identity):

```
message = LP("porta.pairing.v1")
        ‖ LP(secret)
        ‖ LP(inviterDeviceId)
        ‖ LP(joinerDeviceId)
        ‖ LP(joinerPublicKey)
```
где `LP(x)` = 4-байтовая длина (BE) + байты `x`. Длины-префиксы исключают
неоднозначность склейки полей.

joiner подписывает `message` своим приватным ключом и присылает `PairingResponse`
(его Device ID, публичный ключ, имя, подпись).

## Проверка на стороне инициатора (`PairingService.VerifyProof`)

1. Токен не просрочен (по `TimeProvider`).
2. Версия поддерживается.
3. `joinerDeviceId == FromPublicKey(joinerPublicKey)` — личность joiner'а самосогласована.
4. Подпись валидна для `message` под публичным ключом joiner'а.

Только при всех успехах возвращается `TrustedDevice` для сохранения. Ошибки —
типизированный `PairingResult` (`Expired`, `UnsupportedVersion`, `IdentityMismatch`,
`BadSignature`), без исключений на ожидаемые случаи.

## Проверка на стороне joiner'а

joiner доверяет инициатору по токену: `PairingService.CreateInviterTrust(token, name)`
даёт `TrustedDevice` с ключом из QR. Проверка сетевого ключа при подключении
(совпадает ли предъявленный ключ с закреплённым) — на этапе транспорта.

## Границы среза

- Только **логика**: токен, кодек, доказательство, проверки, установление доверия.
- **Сетевого обмена нет** — кто кому и когда шлёт `PairingResponse`, определим на
  Этапе 3 (транспорт QUIC). Здесь всё офлайн-тестируемо.
- Discovery (mDNS) — отдельный срез Этапа 2.
- Защита от перебора кода (rate-limit), длина/энтропия кода под UX — уточнить позже.

## Тесты

- Кодек: round-trip; префикс; порча строки → ошибка; вычисление `InviterDeviceId`.
- Happy path: invite → proof → verify → `Success` с корректным `TrustedDevice`.
- Просроченный токен → `Expired` (через управляемое время).
- Неверный код (атакующий без секрета) → `BadSignature`.
- Подделка личности (id ≠ хеш ключа) → `IdentityMismatch`.
- Подпись чужим ключом → отклонение.
- joiner: `CreateInviterTrust` закрепляет ключ из токена.
