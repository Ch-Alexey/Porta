# 33. Прогресс и отмена

## Зачем

Долг, повторявшийся в четырёх срезах подряд (25–28). Общая суть одна:
**приложение молчит, пока работает**.

- Разовая передача: нажал «Отправить» — и до конца ничего не происходит. На файле в
  несколько гигабайт это неотличимо от зависания.
- Приём: нажал «Принять» — то же самое.
- Синхронизация: результат приходит по завершении.
- Поиск медиа: результаты приходят одним куском в конце.

И вторая половина той же проблемы: **начатое нельзя остановить**. У поиска медиа кнопка
«Стоп» есть, у передачи и синхронизации — нет.

Каркас для прогресса уже готов с обеих сторон: передача идёт кусками по 256 КиБ, блоки
синка — пачками по 4 МиБ. Осталось сообщать о них наружу.

## Границы среза

**Входит:**
- `IProgress<TransferProgress>` в разовой передаче (обе стороны) и в блочном обмене синка.
- Отображение прогресса в UI: «отправлено 12 из 40 файлов, 340 МБ из 1.2 ГБ».
- Кнопка «Отменить» для передачи и синхронизации.
- Поиск медиа отдаёт результаты пачками, а не одним куском в конце.

**Не входит:**
- Возобновление прерванной передачи (обрыв на 90% — заново).
- Ограничение скорости.
- Оценка оставшегося времени: врать пользователю про «осталось 3 минуты» на LAN с
  непредсказуемой скоростью хуже, чем показывать честные байты.

## Модель прогресса

```
TransferProgress = FilesDone, FilesTotal, BytesDone, BytesTotal, CurrentFile
```

Одна запись на все три сценария (отправка, приём, синк) — у них одинаковая форма отчёта.
`BytesTotal` известен заранее в передаче (из предложения) и в синке (из запроса блоков),
поэтому проценты честные, а не выдуманные.

Отчёты идут через `IProgress<T>` — стандартный механизм .NET: ядро не знает про UI-поток,
а view-модель получает вызовы там, где создала `Progress<T>`.

**Частота.** Отчёт на каждый кусок в 256 КиБ — это сотни вызовов в секунду на быстром
канале, то есть UI будет занят перерисовкой вместо работы. Поэтому прогресс
прореживается по времени: не чаще одного отчёта в 100 мс, плюс обязательный финальный.

## Отмена

Отмена — это `CancellationToken`, который уже прокинут по всем путям; не хватало только
кнопки и источника токена во view-моделях.

Важно, что происходит при отмене посреди передачи:
- **отправитель** просто прекращает слать — соединение рвётся;
- **получатель** видит обрыв на чтении; недописанный файл лежит во времянке
  `.porta-drop` и удаляется в `catch`.

То есть отмена не оставляет мусора и не портит уже принятые файлы. Это проверяется
тестом, а не предполагается.

## Тесты

- Передача большого файла отдаёт несколько отчётов, последний — с полными числами.
- Отчёты прореживаются: на много мелких кусков их заметно меньше, чем кусков.
- Приём отдаёт прогресс по файлам.
- Отмена посреди передачи: исключение отмены, времянки не остались, ранее принятые
  файлы целы.
- Блочный обмен синка отдаёт прогресс по байтам.
- View-модели: прогресс виден, кнопка отмены доступна только во время работы, отмена
  приводит к внятному сообщению.
- Медиа: результаты приходят пачками (а не только в конце).
