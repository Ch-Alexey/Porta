# Фича: версионированный синк (срез D)

**Статус:** первый срез готов (односторонний версионированный pull) · **Слой:** `Porta.Core/Sync`, `Porta.Core/Data`, `Porta.Core/Protocol`

Готово: миграция 002 + `FileIndexRepository`, `VersionedFolderIndexMessage`,
`VersionedSync` (Rescan/Serve/Pull с разрешением конфликтов и персистентностью).
6 тестов (4 репозиторий + 2 синк in-memory) + интеграционный поверх QUIC.

Финальный срез конфликтов: связывает [версии](13-version-vectors.md),
[версионированный индекс](14-versioned-index.md), [решение](15-conflict-resolution.md),
[применение](16-conflict-apply.md) и **персистентность** в единый рабочий синк с
конфликтами между устройствами.

## Персистентность

`FileIndexRepository` (SQLite, миграция 002) хранит версионированный индекс на хранилище.
Вектора версий переживают перезапуск — иначе при каждом старте всё выглядело бы новым.

**Rescan** = загрузить прежний индекс → просканировать папку → `IndexVersioning.Apply`
(инкремент версий изменившихся файлов) → сохранить → вернуть.

## Протокол

- Запрос: `FolderIndexRequest(storageId)`.
- Ответ: `VersionedFolderIndexMessage(storageId, entries)` — индекс с версиями.
- Блоки: как раньше (`BlockRequestMessage`/`BlockResponseMessage`).

## Поток (`VersionedSync`)

**ServeAsync:** rescan → отдать версионированный индекс → отдавать блоки по запросу.

**PullAsync:** rescan локального → запросить и получить удалённый версионированный индекс →
по каждому файлу `ConflictResolver.Decide` → собрать недостающие блоки (для Accept/Conflict,
с дедупликацией) → получить блоки → `SyncApplier.Apply` (пишет принятые файлы и конфликтные
копии) → **сохранить обновлённый индекс** (для принятых — принять версию удалённого).

## Границы среза

- Односторонний pull с версиями, конфликтами и персистентностью — **с тестами** (in-memory).
- Встречный проход (полная двусторонняя конвергенция за один сеанс), удаления, сжатие
  векторов — дальнейшие срезы.
- Конфликтные копии попадут в индекс при следующем rescan (осознанно).

## Тесты

- Свежий pull: у A файл, у B пусто → B получает файл и **принимает версию A** (в БД).
- Параллельная правка (версии конкурентны) → у B создаётся конфликтная копия, локальный
  файл не тронут.
