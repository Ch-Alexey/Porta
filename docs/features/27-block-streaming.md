# 27. Потоковая отдача блоков и таймаут чтения

## Зачем

Дефект, найденный и подтверждённый на срезе 26 (см. `docs/features/26-drop-transfer.md`).
Блочный обмен складывает **все** запрошенные блоки в одно `BlockResponseMessage`, а
`MessageChannel` не пропускает сообщения больше 16 МБ. Эксперимент — синк папки с
файлом 20 МБ:

```
отдающая сторона: InvalidOperationException «Сообщение больше лимита 16777216 байт»
принимающая сторона: WaitingForActivation — висит вечно
```

Два отдельных дефекта в одном сценарии:

1. **Потолок 16 МБ.** Синхронизация папки с фотографиями упирается сразу — это не
   экзотика, это обычное первое использование.
2. **Зависание навсегда.** Таймаута на чтение нет, поэтому любая смерть второй стороны
   (не только эта) вешает нашу сторону мёртвым ожиданием. Второй дефект опаснее
   первого: он превращает любую ошибку в зависший процесс.

Есть и третья беда, вылезающая сразу за первой: `MemoryBlockSource` держит **все**
полученные блоки в памяти. Даже с нарезкой на сообщения синк папки на 5 ГБ съест 5 ГБ
RAM. Чинить потолок, оставив это, — значит поменять падение на OOM.

## Границы среза

**Входит:**
- `BlockBatchMessage` — блоки идут пачками с явным признаком последней.
- `BlockStreaming` — общая отправка/приём пачек (бюджет по байтам, а не по количеству).
- `SpooledBlockSource` — принятые блоки складываются во временную папку, а не в память.
- `MessageChannel.IdleTimeout` — чтение не ждёт вечно.
- `VersionedSync` переведён на всё перечисленное.

**Не входит:**
- `SyncProtocol` — ранний неверсионированный движок, **в приложении не используется**
  (живёт только в своих тестах, вытеснен `VersionedSync`). Тот же дефект в нём есть.
  Не чиню и не удаляю молча: предложу пользователю удалить как мёртвый код.
- Прогресс передачи, докачка, ограничение скорости.

## Пачки

```
принимающая                       отдающая
-----------                       --------
BlockRequestMessage(hashes[]) ->
                              <-  BlockBatch(blocks[], isLast=false)
                              <-  BlockBatch(blocks[], isLast=false)
                              <-  BlockBatch(blocks[], isLast=true)
```

- Бюджет пачки — 4 МиБ содержимого. С запасом под лимит 16 МБ: даже максимальный блок
  (64 КиБ) и накладные MessagePack не выведут пачку за лимит.
- Последняя пачка помечена явно и может быть пустой (запросили нечего, или ничего не
  нашлось).
- Бюджет считается по **байтам блоков**, а не по их числу: блоки разного размера
  (2–64 КиБ), и лимит по количеству либо не защищает, либо режет слишком мелко.

## Приём на диск

`SpooledBlockSource` — `IBlockSource` поверх временной папки: каждый блок ложится
файлом с именем по своему хешу, `TryGet` читает его обратно. Память — размер одной
пачки, а не всей передачи. Папка удаляется при `Dispose`, в том числе если синк упал.

Имя файла — hex хеша, то есть блоки естественно дедуплицируются, а имя не может
выйти за пределы папки (только `[0-9A-F]`).

## Таймаут чтения

`MessageChannel.IdleTimeout` (по умолчанию 2 минуты) ограничивает **одно** чтение, а не
весь диалог: за это время вторая сторона обязана прислать хоть что-то. Долгая передача
не страдает — пачки идут одна за другой; страдает только по-настоящему мёртвый пир.
Истечение — `TimeoutException` вместо вечного ожидания.

## Тесты

- Синк файла 20 МБ проходит целиком (тот самый сценарий, что падал).
- Блоки приходят несколькими пачками (а не одной) — иначе тест выше ничего не доказывает.
- Пустой запрос блоков: одна пустая последняя пачка, диалог не виснет.
- `SpooledBlockSource`: отдаёт что положили, дедуплицирует, чистит папку на `Dispose`.
- Чтение из молчащего канала падает по таймауту, а не висит.
- Уже существующие тесты синка продолжают проходить (совместимость поведения).
