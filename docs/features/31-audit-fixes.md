# 31. Ревизия: одинаковые файлы и история версий

## Зачем

Проверка проекта по вопросу «что будет, если передать файл, который уже есть на
устройстве». Прогнал три сценария на настоящем движке синка — два оказались
неправильными.

### Что проверялось и что вышло

| Сценарий | Результат | Оценка |
|---|---|---|
| Одно имя, **разное** содержимое, раньше не синхронизировались | конфликт, обе версии сохранены | правильно |
| Одно имя, **одинаковое** содержимое | **создалась конфликтная копия** | **дефект** |
| Обновление файла, `versions=null` (как в приложении) | прежняя версия исчезла бесследно | **дефект** |
| Разовая передача файла, который уже есть байт в байт | **создался дубликат** | **дефект** |
| Нет папки хранилища (поверх QUIC) | падает за ~100 мс с внятным сообщением | правильно |

## Дефект 1: дубликаты при одинаковом содержимом

```
папка B до синка:  фото.jpg = «одинаковое содержимое»
папка B после:     фото.jpg = «одинаковое содержимое»
                   фото.sync-conflict-20260907-150035-AKLRRW4.jpg = «одинаковое содержимое»
```

**Почему.** `ConflictResolver.Decide` сравнивает содержимое только при `Identical`
порядке векторов. Два устройства, никогда не синхронизировавшиеся, имеют
**параллельные** векторы (`{A:1}` против `{B:1}`) — ветка `Concurrent` уходит в
конфликт, не глядя на содержимое.

**Почему это важно.** Это не редкий угол, а самый обычный первый запуск: человек
скопировал папку с фотографиями на второй компьютер (флешкой, из бэкапа), потом
настроил синхронизацию. Каждый файл получил бы копию-двойник. Ровно то, ради чего
пользователь и спрашивает «а что, если файл уже есть».

**Починка.** Одинаковое содержимое — не конфликт: разрешать нечего. Сравнение
контент-хеша идёт **до** разбора порядка векторов. При этом векторы сливаются
(`VersionVector.Merge`), иначе стороны так и остались бы расходящимися и сравнивали
хеши при каждом синке.

## Дефект 2: история версий не подключена

`FileSystemVersionStore` написан на срезе 11 и **нигде в приложении не создаётся** —
`QuicSyncController` вызывает `PullAsync` без него. То есть при обычном обновлении файла
прежнее содержимое затирается без следа, хотя «история версий» заявлена в границах
первой версии (`00-functionality.md` §7).

**Починка.** Голова создаёт `FileSystemVersionStore` в папке данных приложения
(`<data>/versions/<storageId>/`) — **вне** папки хранилища, чтобы архив не попадал в
индекс и не уезжал на другое устройство.

## Дефект 3: разовая передача плодила дубликаты одинаковых файлов

Проверка показала: передача файла, который уже лежит у получателя **байт в байт**,
создавала `фото (2).jpg`. Отправил фотографию дважды — получил три копии.

Сначала я записал это как правильное поведение («явное действие человека, лучше лишняя
копия, чем молча проглотить»). Подумав, считаю довод негодным: цель пользователя —
«чтобы файл был у получателя» — уже достигнута, причём тем же содержимым. Копия ничего
не добавляет, а разгребать её человеку.

**Починка.** Сравниваем **содержимое**, а не имя: если по этому пути уже лежит файл с
тем же контент-хешем, существующий остаётся, копия не создаётся. Разное содержимое под
одним именем по-прежнему кладётся рядом под свободным именем — чужие данные не
затираются никогда.

## Что проверено и оказалось в порядке

- **Нет папки хранилища** (стёрли, отключили внешний диск, опечатка в пути). Поверх
  настоящего QUIC синк падает за ~100 мс с внятным `Папка хранилища не найдена: <путь>`
  — и у отдающей стороны, и у принимающей.

  Оговорка: на in-memory каналах, которыми написана часть тестов, тот же сценарий
  выглядел как зависание до таймаута. Разницу даёт разрыв соединения, которого у
  дуплексных пайпов нет. То есть **этот класс проверок надо делать поверх настоящего
  транспорта** — иначе можно и придумать несуществующий дефект, и пропустить настоящий.
- Пустые папки с обеих сторон — синк проходит вхолостую, без ошибок.
- Отдающая сторона не делится хранилищем — принимающая получает пустой индекс, файлы
  не трогаются.

## Тесты

- Одинаковое содержимое при параллельных векторах: конфликтная копия **не** создаётся,
  файл остаётся один.
- Векторы после такого синка слиты — повторный синк ничего не делает.
- Разное содержимое при параллельных векторах: конфликт по-прежнему создаётся
  (починка не должна проглотить настоящее расхождение).
- Обновление файла с подключённым хранилищем версий: прежнее содержимое лежит в архиве.
- Архив создаётся вне папки хранилища и не попадает в индекс.
- Разовая передача одинакового файла: дубликат не создаётся, времянка не остаётся.
