# 28. Разовая передача: интерфейс (срез 2)

## Зачем

На срезе 26 ядро научилось передавать файлы с подтверждением получателя, но из
приложения этим воспользоваться нельзя: `BackgroundSyncListener` не передаёт
`IDropAcceptance`, поэтому входящие передачи вежливо отклоняются. Фича есть в коде и
отсутствует для пользователя. Этот срез её включает.

Закрывает §4.2 «Отправить (разовая передача)» из `00-functionality.md`.

## Границы среза

**Входит:**
- Вкладка «Передача»: выбрать файлы, выбрать устройство из найденных, отправить.
- Входящие предложения: «Принять файлы от устройства A?» с кнопками принять/отклонить,
  список файлов и общий объём.
- Папка «Загрузки» — куда складываются принятые файлы; хранится в БД, меняется в UI.
- Системный диалог выбора файлов (на десктопе).

**Не входит:**
- Прогресс передачи (ядро отдаёт результат по завершении).
- Отправка папки целиком — только файлы.
- Отправка из вкладки «Медиа» (кнопка «отправить найденное») — следующий шаг, когда
  этот путь устоится.
- Полноценная вкладка «Настройки» (§4.6): здесь появляется только папка загрузок,
  рядом с тем местом, где она осмысленна.

## Настройки в БД

Таблица `settings (key, value)` заведена ещё миграцией 001 и до сих пор не
использовалась — беру её, новая миграция не нужна.

`SettingsRepository` — простое key/value. Первый ключ: `downloads.folder`.
По умолчанию — `<Загрузки пользователя>/Porta`, чтобы принятое не смешивалось с
браузерными скачиваниями.

## Кто кого спрашивает

Ядро на приёме зовёт `IDropAcceptance.DecideAsync` и **ждёт ответа**. Ответ должен
прийти от человека, то есть из UI. Связка:

```
QUIC-приём (фон)                UiDropAcceptance            вкладка «Передача»
      |                                |                            |
   ReceiveAsync -> DecideAsync -------->|                            |
      |                          кладёт предложение в очередь -----> показывает карточку
      |                          ждёт TaskCompletionSource           |
      |                                |<--- Принять / Отклонить ----|
      |<------- DropDecision ----------|                            |
```

Важные детали:
- **Ожидание не бесконечно.** Если у экрана никого нет, отправитель не должен висеть:
  через 2 минуты предложение само отклоняется («Получатель не ответил»). Это
  согласуется с `MessageChannel.IdleTimeout` из среза 27.
- Предложение приходит из фонового потока — в коллекцию UI кладётся через
  `IUiDispatcher`, как это уже сделано для найденных устройств.
- Решение по каждому предложению принимается один раз; повторные нажатия игнорируются.

## Отправка

`IDropController` (по образцу `ISyncController`): «отправить эти файлы этому
найденному устройству». Реализация на QUIC живёт в десктоп-голове, view-модель знает
только абстракцию и потому тестируется без сети.

Выбор файлов — через `IFilePicker`, чтобы view-модель не зависела от Avalonia
`IStorageProvider`. Десктопная реализация открывает системный диалог; в тестах
подставляется фейк.

## Что увидит пользователь

- **Отправить:** кнопка «Выбрать файлы…», список выбранного с общим объёмом, выпадающий
  список найденных устройств, кнопка «Отправить», строка статуса.
- **Принять:** карточка входящего предложения — имя устройства, число файлов и объём,
  кнопки «Принять» и «Отклонить».
- **Папка загрузок:** поле с путём и кнопка «Сохранить».

## Тесты

- `SettingsRepository`: значения по умолчанию, запись, перезапись, персистентность.
- `UiDropAcceptance`: предложение попадает в очередь; «Принять» отдаёт решение с папкой;
  «Отклонить» — отказ с причиной; отсутствие ответа даёт отказ по таймауту; повторное
  решение по тому же предложению игнорируется.
- `TransfersViewModel`: выбранные файлы показываются с объёмом; отправка без устройства
  или без файлов не идёт; успешная отправка отражается в статусе; ошибка контроллера
  не роняет UI; смена папки загрузок сохраняется.
