# Фича: Identity — личность устройства

**Статус:** первый срез готов (28 тестов зелёные) · **Слой:** `Porta.Core/Identity`

Реализовано: `Base32`, `DeviceId`, `DeviceIdentity` (ECDSA P-256, подпись/проверка),
`IDeviceIdentityStore` + `FileDeviceIdentityStore`. Осталось (см. ниже): TLS-сертификат
для QUIC — на этапе транспорта; защищённое хранилище ключа — задача в roadmap.

## Зачем

Каждое устройство должно иметь постоянную криптографическую личность. На ней держатся:

- **Device ID** — стабильный идентификатор устройства (показывается в UI, участвует
  в связывании через QR/ссылку).
- **Доверие** — при связывании устройства обмениваются публичными ключами и потом
  проверяют друг друга по ним (pinning).
- **Шифрованный транспорт** — из ключа устройства делается самоподписанный
  TLS-сертификат для QUIC ([ADR-0006](../adr/0006-transport-quic.md)).

Решение [ADR](../adr/0002-target-platforms.md): **новое устройство = новая личность**,
ключи не экспортируются и не переносятся.

## Выбор криптографии

- **Алгоритм ключа: ECDSA P-256 (nistP256).** Причина — один и тот же ключ должен
  годиться и как идентити, и как ключ TLS-сертификата для QUIC. ECDSA P-256
  надёжно поддерживается TLS 1.3 во всех стеках (в отличие от Ed25519, поддержка
  которого в QUIC/schannel неоднородна — см. риски в ADR-0006).
- **Device ID: Base32(SHA-256(SubjectPublicKeyInfo)).** Хешируем DER-представление
  публичного ключа (SPKI), кодируем в Base32 (RFC 4648, без padding, верхний
  регистр), разбиваем на группы для читаемости. Так же по духу, как Device ID в
  Syncthing (там — Base32 от SHA-256 сертификата с check-цифрами).

> Контрольные цифры на группы (Luhn mod N, как в Syncthing) — возможное улучшение
> позже, чтобы ловить опечатки при ручном вводе ID. Пока не делаем.

## Модель (первый срез)

- `DeviceId` — value-object вокруг строки-идентификатора: нормализация, разбор,
  форматирование по группам, сравнение. Вычисляется из публичного ключа.
- `DeviceIdentity` — личность: пара ключей ECDSA + производный `DeviceId`.
  Умеет отдавать публичный ключ (SPKI) и подписывать/проверять (для будущего
  протокола связывания). Создание — генерация новой пары.
- `IDeviceIdentityStore` — абстракция хранения личности.
- `FileDeviceIdentityStore` — реализация: приватный ключ (PKCS#8) в файле в папке
  данных приложения. `LoadOrCreate()` — загрузить существующую или создать новую.

### Хранение ключа — важное замечание

На первом срезе приватный ключ лежит в файле в папке данных приложения (права
доступа — только пользователю). Это **временно**. Позже подключим платформенное
защищённое хранилище (DPAPI/Keychain/Keystore) через абстракцию `IDeviceIdentityStore`,
не меняя остальной код. Помечено как задача в [roadmap](../roadmap.md).

## Что НЕ входит в этот срез

- Генерация TLS-сертификата для QUIC (сделаем на этапе транспорта, но ключ уже готов).
- Защищённое платформенное хранилище ключа.
- Протокол связывания (использует эту личность, но проектируется отдельно — Этап 2).

## Тесты

- Base32: соответствие RFC 4648 (известные векторы), round-trip.
- `DeviceId`: детерминированность (один ключ → один ID), формат/группировка,
  разбор строки обратно.
- `DeviceIdentity`: генерация даёт валидный ID; подпись проверяется своим ключом и
  не проходит чужим.
- `FileDeviceIdentityStore`: `LoadOrCreate` создаёт при отсутствии и возвращает ту же
  личность при повторном вызове (round-trip через диск).
