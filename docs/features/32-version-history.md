# 32. История версий: ротация и откат

## Зачем

Долг из ревизии (срез 31). Архив прежних версий заработал, но:

- **копится без ограничений** — каждое обновление файла кладёт копию, ротации нет;
  на активно меняющемся хранилище это будет расти, пока не кончится диск;
- **не виден пользователю** — файлы лежат в папке данных приложения, откатиться из
  приложения нельзя. Сценарий «Откат версии» из `00-functionality.md` §5 невыполним.

То есть заявленная в границах v1 «история изменений файлов» есть наполовину: система
бережёт данные, но человек не может ими воспользоваться.

## Границы среза

**Входит:**
- Ротация: хранить не больше N версий файла, лишние (самые старые) удалять.
- Перечисление: какие файлы хранилища имеют версии и какие именно.
- Откат: восстановить выбранную версию в папку хранилища.
- Раздел «История версий» на вкладке «Хранилища».

**Не входит:**
- Ограничение архива по общему объёму или по возрасту (только по числу версий на файл).
- Просмотр содержимого версии до отката и сравнение версий.
- Версии для разовых передач — они не отслеживаются, это не хранилище.

## Ротация

`FileSystemVersionStore` получает `MaxVersionsPerFile` (по умолчанию **10**). После
записи новой версии лишние старые удаляются. Порядок определяется именем файла
(`имя~ГГГГММДД-ЧЧММССмс.ext`) — оно монотонно по времени, поэтому сортировка строк
совпадает с сортировкой по времени и лишний доступ к ФС не нужен.

Почему по числу, а не по объёму: понятная гарантия («последние 10 правок»), которую
пользователь может держать в голове. Лимит по объёму осмысленнее для больших архивов,
но требует обхода всего дерева при каждой записи.

## Откат

Восстановление **сначала архивирует текущий файл**, потом кладёт на его место
выбранную версию. Иначе откат сам стал бы способом потерять данные: передумал —
вернуть нечего.

После отката файл в папке хранилища меняется, поэтому очередной скан увидит новое
содержимое и разошлёт его как обычную правку. Это правильное поведение: откат — такое
же изменение файла, как любое другое.

## Где живёт

`IVersionArchive` в ядре — «архив версий всех хранилищ»: перечислить файлы с версиями,
перечислить версии файла, откатить. Реализация `FileSystemVersionArchive` — поверх
папки данных приложения, по подпапке на хранилище. Она же выдаёт `IVersionStore` для
конкретного хранилища, который используется синхронизацией.

Так голова перестаёт собирать пути руками (раньше `QuicSyncController` склеивал
`<data>/versions/<storageId>` сам), а UI получает архив за абстракцией и тестируется
без файловой системы... точнее, с временной папкой, но без сети и БД.

## Тесты

- Ротация: после N+3 обновлений остаётся ровно N версий, и это самые свежие.
- Ротация не задевает версии других файлов и других хранилищ.
- Перечисление: файлы с версиями и версии файла отсортированы от новых к старым.
- Откат возвращает прежнее содержимое.
- Откат архивирует текущее содержимое (можно откатить откат).
- Откат неизвестной версии — внятная ошибка, файл не тронут.
- Путь версии не может увести за пределы папки хранилища.
- View-модель: выбор хранилища показывает файлы с версиями; откат зовёт архив и
  сообщает результат.
